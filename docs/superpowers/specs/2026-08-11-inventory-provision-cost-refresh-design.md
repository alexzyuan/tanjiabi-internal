# 库存计提成本刷新设计

## 目标

库存计提增加一个明确、可追溯的“刷新成本”操作。用户查看任一历史月时，操作会以产品管理当前维护的采购成本和单位头程成本重算该月及其比较月的库存计提；德国店铺 `tanjia-eu-DE`（SID `17307`）必须进入这条数据链路。

这是按当前成本回算历史月的管理口径，不是还原月末当时的产品成本。

## 已确认范围

- 用户选择历史月（例如 `2026-05`）后点击“刷新成本”。
- 以当前产品管理成本覆盖该月库存批次的单位采购成本、单位头程成本，并重算库存金额、期末计提余额、本月新增计提、已计提冲回与本月计提金额。
- 为保证环比口径一致，同时刷新上一个比较月（例如 `2026-04`）的成本；`2026-04` 与 `2026-03` 的起始余额关系同样适用。
- 德国范围至少包含领星店铺目录中的 `tanjia-eu-DE`（SID `17307`）。刷新操作强制更新店铺目录，避免旧的店铺目录缓存漏掉该店铺。
- 普通“刷新计提”保持原语义：加载计提数据但不主动以产品管理成本覆盖历史缓存。
- 当前月不提供“刷新成本”：当前月继续由实时 FBA 库存接口返回的成本字段计算。用户必须选择历史月才能执行产品管理成本回算。

## 数据流

```mermaid
flowchart LR
  A["选择历史月并点击刷新成本"] --> B["刷新领星店铺目录"]
  B --> C["读取选中月和比较月的历史库存/库龄"]
  C --> D["按 SID + MSKU 查询 Listing"]
  D --> E["Listing local_sku 映射"]
  E --> F["产品管理查询采购成本、单位头程成本"]
  F --> G["校验每个库存 SKU 的完整成本"]
  G --> H["逐月原子写入两个月历史缓存"]
  H --> I["重新计算并返回库存计提"]
```

1. 历史库存数量、月末库存金额结构和 FIFO 库龄来源仍是领星 FBA 月末库存报表与库存分类账。成本刷新会强制重新读取目标月和比较月的历史库存源，以便使用最新店铺目录并将德国店铺纳入范围；对原本已在范围内的库存批次，只覆盖成本，不改写数量、批次月份或库龄。
2. 每个库存行以 `sid + msku` 查询已配对 Listing，取得 `local_sku` / 内部 SKU。
3. 按内部 SKU 批量查询领星产品管理。采购成本使用产品管理的采购成本字段；单位头程成本使用产品管理返回的单位头程字段。两类字段均记录实际匹配的字段名，避免接口字段变化时无声取错值。
4. 刷新同时强制绕过历史库存缓存、店铺目录缓存和共享商品目录缓存。产品管理、Listing、店铺目录、历史库存或库存分类账任一请求失败时操作失败；不写入半成品缓存，也不回退为旧成本。
5. 若任何可计提库存行没有 Listing 映射、产品管理记录、采购成本或头程成本，操作失败并返回可定位的 SID、店铺、MSKU、内部 SKU（若已解析）和缺失原因。不得把缺失成本当作 `0`，不得覆盖原历史缓存。
6. 两个目标月份先在内存完成成本覆盖与校验，只有全量校验通过才开始逐月原子写入缓存。若缓存写入发生文件系统错误，操作必须明确报告已写入的月份与未写入的月份，停止后续写入并记录恢复所需的错误上下文；不得伪造成功结果。

## 模块边界

### `src/services/inventoryProvisionCostRefreshService.js`（新增）

拥有“成本刷新”的完整编排：强制刷新店铺目录、筛选业务店铺、调用历史库存加载器、批量 Listing 与产品管理查询、成本字段解析、缺失成本诊断、刷新结果摘要。它不计算库龄、计提金额或渲染 UI。

该服务暴露一个面向路由的函数，输入为选择月份，输出为：刷新月份、比较月份、匹配/更新/失败行计数、产品管理读取时间和结构化诊断。日志带 `month`、`comparisonMonth`、`sid`、`storeName`、`msku`、`internalSku`、`stage`、`matchedField`，但不记录认证信息或完整产品原始响应。

### `src/services/inventoryProvisionService.js`（扩展）

保留现有的历史库存、FIFO 库龄和计提计算职责。提取可供刷新服务调用的受控历史月加载/持久化接口；计提读取继续通过相同历史缓存获得成本已刷新后的行。普通读取不得悄悄发起产品管理刷新。

### `server.js`（扩展）

增加受财务权限保护的 `POST /api/dashboard/inventory-provision/refresh-costs`。请求体仅接受 `date`（`YYYY-MM`），调用成本刷新服务后返回刷新摘要；前端随后按当前筛选重新加载库存计提。错误响应保留安全的诊断信息。

### `assets/js/features/inventory-provision.js`（扩展）

在现有“刷新计提”旁新增“刷新成本”。点击后先显示明确确认文案：当前产品管理成本会回算所选历史月和上月；确认后调用新接口、禁用重复提交、重渲染看板。状态区域展示成本刷新时间和匹配统计；失败时显示可操作的错误摘要，不清空当前表格。

### `index.html`（扩展）

仅增加语义化原生按钮和其可访问标签。复用既有 `.primary-button` / 按钮状态样式，不增加新的视觉 token 或页面专属 CSS。

## 德国店铺

`filterCoreSellers` 已将 `DE`/德国视为业务国家，`lingxingShopMap` 也已有 `tanjia-eu-DE`（SID `17307`）的稳定映射。实现需要覆盖两个风险点：

- 刷新成本时不复用过期店铺目录，保证目录中有该 SID 后才开始 FBA、Listing 与产品管理查询。
- 对领星 FBA EU 合并仓返回 `sid = 0` 的记录，沿用现有 `seller_group_name` → `tanjia-eu-DE` 的归属规则；最终成本查询使用规范 SID `17307`。

不会创建假店铺或用显示名称猜测 SID；如果运行时店铺目录缺少 SID `17307`，操作必须失败并指出目录异常。

## 缓存与一致性

- 历史库存缓存继续按月份保存，但增加成本刷新元数据：`costSource = 产品管理`、`costRefreshedAt`、`costRefreshMonth`、`costRefreshSummary`。
- “刷新成本”只在目标月及其比较月同时验证成功后开始覆写缓存；普通历史读取仍展示原有缓存时间，并额外展示最近成本刷新时间（若有）。缓存写入异常会显式暴露已写入/未写入月份，操作员必须重试，不能将该状态当作成功。
- 不改变当前月实时库存的加载策略：当前月依旧实时取 FBA 库存，并且“刷新成本”按钮在当前月被禁用并说明此限制。

## 失败策略与可观测性

- Listing、产品管理、店铺目录、历史库存或缓存写入失败均直接失败；不吞错、不用零成本兜底、不覆盖旧缓存。
- 返回与记录按阶段分组的失败数和最多若干条 SKU 样例，供页面提示和服务端排查。
- 成功日志记录目标月、比较月、店铺数量、行数、更新数、未匹配数、请求耗时和缓存写入结果。

## 验证

自动化测试覆盖：

1. `tanjia-eu-DE`（SID `17307`）被纳入刷新范围，且 EU 合并仓 `sid = 0` 正确归属。
2. Listing 的 MSKU→内部 SKU 映射后，产品管理采购成本与单位头程成本覆盖历史库存行。
3. 选择 `2026-05` 时，`2026-05` 与 `2026-04` 均使用同一次最新成本刷新，计提差额按新成本计算。
4. 缺 Listing、缺产品、缺任一成本字段或上游请求失败时，刷新失败且旧缓存不被覆盖。
5. 普通“刷新计提”不调用产品管理成本刷新。
6. 路由鉴权、请求参数校验和前端按钮 busy/错误/成功状态。

浏览器验证覆盖：目标页面无控制台错误；按钮可用鼠标和键盘操作；确认后请求体含选择的 `date`；德国筛选能显示 `tanjia-eu-DE`；成功与失败状态都可读且不造成窄屏溢出。

## 不在范围内

- 不修改库存月末数量、FIFO 库龄算法、计提比例或利润口径。
- 不刷新其他仪表板、销售利润报表或采购模块的成本。
- 不建立定时全量历史成本回算任务。
- 不修改生成后的 `styles.css`，也不新增前端框架或 React 组件。

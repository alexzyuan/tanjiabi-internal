# 库存计提当年成本全量刷新设计

## 目标

将库存计提的“刷新成本”改为一次性刷新当年全部已结束月份。每个历史月份保留已有的月末库存数量、库龄、计提逻辑和负责人数据，仅以领星产品管理当前返回的采购成本与单位头程物流成本覆盖缓存中的成本字段。

当前月份继续使用实时 FBA 成本，绝不被本操作覆盖。

## 范围与口径

- 刷新范围是当年 `01` 月至当前月前一个月；例如运行日在 `2026-08`，刷新 `2026-01` 至 `2026-07`。
- 每月的成本均取刷新时领星产品管理 API 的最新值，不按历史成本日期回溯。
- 成本字段沿用现有产品管理字段优先级：采购成本和单位头程物流成本均必须存在且为有效数字。
- 历史缓存必须已存在且包含行数据；任一目标月份缺失缓存、任一行不能解析出成本匹配标识、无法从当前店铺或 MSKU 国家店铺取得 Listing 内部 SKU、或产品管理成本缺失时，整个请求失败，不写入任何月份。例外是：Listing 明确存在但已删除且 `local_sku` 为空的行，保留原成本并跳过，同时返回“店铺 / MSKU 需要配对”的可见提醒。
- 接口成功后显示统一的“成本缓存刷新时间”，并列出覆盖月份和更新行数。

## 设计

### `src/services/inventoryProvisionCostRefreshService.js`

该服务拥有批量成本刷新编排：

1. 计算当年已结束月份。
2. 直接读取每个月既有的历史库存缓存，不调用历史库存、库存分类账、库龄或负责人加载 API。
3. 汇总所有缓存行的 `SID + MSKU`，只按库存中实际出现的标识精确请求 Listing；当前店铺没有返回时，根据 MSKU 国家前缀回查同品牌国家店铺，并记录成本国家。
4. 解析内部 SKU 后按批次请求领星产品管理 API，采购成本取产品管理当前值，头程成本取回查国家的 `${countryCode}_cg_transport_costs`。
5. 对已删除且 `local_sku` 为空的 Listing 保留原成本并记录跳过原因；其他匹配失败仍在写入前报错。所有校验完成后，顺序写回各月份缓存；写入失败返回已写入与待写入月份，且不静默成功。

完成及失败日志必须包含操作标识、年度、月份数、行数、Listing/产品请求数和各阶段耗时；不得记录认证信息或完整的外部原始响应。

### 路由与前端

`POST /api/dashboard/inventory-provision/refresh-costs` 仍受财务权限保护，前端不再传所选月份。接口忽略月份筛选，始终执行当前年度已结束月份全量刷新。

`assets/js/features/inventory-provision.js` 保留按钮的重复提交保护。确认文案说明“将使用产品管理当前成本刷新本年度已结束月份”；成功后重新加载当前看板，并显示刷新范围、更新行数、成本缓存刷新时间。失败时保留当前表格并展示服务端明确错误。

### 明确不改动

- `src/services/inventoryProvisionService.js` 的历史库存、库龄、计提计算与当前月实时库存逻辑。
- 缓存文件原子写入机制。
- 产品管理成本字段优先级和德国店铺运行时目录校验。
- CSS、表格布局及生成的 `styles.css`。

## 异常与一致性

刷新不会将缺失成本替换为 `0`，不会使用过期成本兜底。除明确标记为“已删除且需配对”的 Listing 行外，所有成本校验在写缓存之前完成；这些跳过行保留旧成本并在响应、缓存摘要和页面状态中列出。若外部 API 调用失败，响应包含对应阶段与安全错误摘要；若缓存写入阶段失败，响应包含已写月份，便于人工核验。

## 验证

自动化测试覆盖：

- 在 2026 年 8 月运行时，读取并更新 2026-01 至 2026-07 的既有缓存。
- 不调用历史库存重建加载器。
- 同一个 SKU 在多个月份复用一次产品管理匹配结果。
- 缺失缓存或任一成本字段时，所有月份保持未写入状态。
- 前端确认文案、无请求月份载荷、成功状态文本和失败状态文本。

上线前运行相关 Node 测试、全量测试与静态检查；部署后核验健康检查、接口耗时日志和一次受控刷新结果。

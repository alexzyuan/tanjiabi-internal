# Filter CSS Ownership Cleanup

## Goal

Make the shared filter components the enforceable single source of truth for filter layout and focus presentation. Remove live, legacy, and dead page-level rules that currently duplicate or override that contract, and strengthen structural tests so equivalent aliases cannot reintroduce the same problem.

## Scope and ownership

- `assets/css/components/30-surfaces-and-filters.css` owns the ordinary `.filters` layout, field sizing, control presentation, and focus treatment.
- `assets/css/components/35-filter-toolbar.css` owns the compact `.filter-toolbar` layout and sizing contract.
- `assets/css/pages/*` may position a business panel or control visibility, but may not establish a private filter or toolbar baseline.
- `assets/css/legacy/current.css` may not declare shared filter or toolbar structure.
- `test/stylesStructure.test.js` owns the static boundary that rejects forbidden page and legacy declarations.
- `styles.css` remains generated by `npm run build:css` and is never edited directly.
- Business JavaScript, backend services, API behavior, table presentation, and unrelated page layout are out of scope.

## Cleanup rules

1. Remove the clearance calculator's `.clearance-rate-panel` filter-grid, label-layout, input-width, and narrow-width grid overrides. The live element already uses `.filters`, whose shared flex contract must determine its presentation.
2. Remove the legacy responsive `.filters` selector from the grouped grid declaration. The other responsive grid selectors remain unchanged.
3. Remove the unused `.fba-shipment-order-toolbar` blocks, including descendant widths, control sizing, and narrow-width behavior. Shipment-order panel, summary, status, and table rules remain intact.
4. Change shared filter and form control focus selectors from `:focus` to `:focus-visible`. The visual treatment continues to use `--tj-action-blue` and `--tj-focus-ring`.

## Structural guard

The structural test must inspect both `assets/css/pages/*` and `assets/css/legacy/current.css`. It must detect shared names and aliases based on selector identity instead of a short allowlist:

- `.filters` and `.filter-toolbar`;
- classes ending in `-filters` or `-toolbar`;
- descendants of those selectors when they set a filter baseline declaration;
- aliases attached to live shared filter markup, such as `.clearance-rate-panel` on an element that also has `.filters`.

Forbidden baseline declarations include container display and layout, gap and padding, border and radius, control height and width, flex sizing, alignment, type styling, focus outline, and shadow. Existing visibility-only exceptions for the sales global filters remain allowed because they do not redefine visual structure.

The test must not depend on indentation or a selector being the first item in a comma-separated group. A focused fixture or direct source assertion will first demonstrate that the current clearance, legacy, and generic toolbar cases fail before production CSS is changed.

## Error handling and compatibility

This work removes ineffective or unreferenced rules instead of adding compatibility fallbacks. Unexpected page-level ownership is reported as a test failure containing the source file and normalized violating rule. The build must fail rather than silently accepting an unknown private filter baseline.

The shared component class names and markup contracts do not change, so feature JavaScript and filter behavior remain compatible.

## Verification

1. Run the focused structural test in the red state and confirm it reports the known clearance, legacy, and private-toolbar violations.
2. Apply the CSS cleanup and focus change, then rerun the focused test in the green state.
3. Run `npm run build:css`, the full `npm test`, and `npm run check`.
4. Start the local application and inspect the clearance filter area at desktop and narrow viewports.
5. Verify mouse interaction, keyboard focus visibility, multi-select summaries, control containment, and absence of console errors.
6. Confirm the generated `styles.css` contains the shared rules and no removed page or legacy filter baseline.

Deployment is not part of this cleanup unless the operator requests it separately after verification.

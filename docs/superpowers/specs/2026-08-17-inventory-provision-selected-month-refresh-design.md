# 库存计提当前月刷新设计

## 目标

库存计提页面的“刷新计提”必须重建当前页面选中的历史月份，而不是仅重新读取缓存。刷新成功后才以新数据替换该月缓存；任何失败都必须保留旧缓存并返回可定位的错误。

## 范围

- 新增受财务权限保护的 `POST /api/dashboard/inventory-provision/refresh`。
- 请求体只接受当前选中的 `date`（`YYYY-MM`）。
- 仅允许刷新历史月份；当前月继续使用实时库存读取，不通过此操作写入伪月末历史缓存。
- 刷新目标月时，沿用 `loadHistoricalInventoryRows(date, { forceRefresh: true })` 的领星历史库存、分类账、FIFO 重建与整数数量校验。
- 页面成功后直接渲染该次刷新返回的数据；普通加载、筛选和上月计提冲回比较继续只读缓存。

## 缓存保护与回退

1. 刷新开始时读取目标月的现有缓存。缓存不存在不阻止首次构建，但结果中必须明确标记无可回退版本。
2. 完整重建完成前不得写入目标缓存。任何上游、匹配、FIFO 或整数校验失败均保留旧文件。
3. 写入前把原缓存保存为目标月专属刷新备份，记录月份、备份时间、刷新操作 ID 和原缓存更新时间。
4. 新缓存通过原子写入替换目标文件。备份写入或新缓存写入失败必须使刷新失败，并保留原缓存。
5. 每月只保留有限数量的最近刷新备份；清理不能删除当前正式缓存。保留数量、备份路径和恢复入口由缓存工具集中维护，不能散落在路由或前端。

## 接口与前端

- 页面“刷新计提”按钮弹出确认，说明会从领星重新构建所选月，并保留该月旧缓存。
- 前端发送 `POST`，不使用带副作用的 `GET?forceRefresh=1`。
- 成功状态显示月份、缓存刷新时间、FIFO 批次数、原始库存记录数和备份是否创建。
- 失败状态显示服务端中文错误；不把网关 HTML 误解析成 JSON 错误。
- `刷新成本`保持独立：它更新已结束月份的采购成本和头程成本，不重建库存数量、库龄或 FIFO。

## 数据流

1. 用户选定历史月份并点击“刷新计提”。
2. 路由校验月份和权限，创建刷新操作 ID。
3. 服务读取旧缓存，调用强制历史重建。
4. 服务校验月末数量和每个 FIFO 批次数量均为整数。
5. 服务保存旧缓存备份，原子写入新缓存。
6. 服务用新目标月缓存计算当前视图；上月比较保持缓存读取。
7. 页面渲染返回结果和刷新元数据。

## 错误与可观测性

- 所有失败日志包含操作 ID、月份、阶段、旧缓存是否存在、是否已创建备份以及错误文本。
- 历史库存缺失、分类账缺失、FIFO 数量不一致、小数数量、备份失败、缓存写入失败均为显式失败，不得降级为旧数据并报告刷新成功。
- 不在刷新请求中自动重建相邻月份或本年度其它月份。

## 验证

- 服务测试：成功刷新只强制重建目标月；失败不调用缓存写入；写入前创建备份；整数校验失败不覆盖旧缓存。
- 路由测试：仅 `POST` 可刷新，传递选中月份，当前月和非法月份被拒绝。
- 前端测试：按钮发出当前月份 `POST`、成功渲染、失败文案清晰。
- 回归：库存计提服务、路由和前端定向测试；全量 `npm test`、`npm run check`、`git diff --check`。

# 销售复盘预算唯一性

## 背景

销售复盘的 MSKU 明细以预算文件中的每条 MSKU 行作为展示基准。生产环境中，`探嘉美国-2026年7月预算.xlsx` 的工作簿内预算月份为 `2026-08`，同时又存在正确命名的 `探嘉美国-2026年8月预算.xlsx`。两份文件均进入 2026-08 的预算上下文，造成同一店铺和 MSKU 的明细重复。

订单利润源数据没有重复；负责人筛选仅过滤已经生成的明细，不能造成该问题。

## 目标

1. 任意预算上下文中，同一 `storeName + month` 只能有一份已解析预算。
2. 检测到重复时，不得合计、覆盖或任意选择其中一份；请求应以可追溯错误失败，并列出冲突文件。
3. 修复后，销售复盘的 MSKU 明细每个店铺和 MSKU 只展示一行预算明细。
4. 清理已确认的生产误标文件 `探嘉美国-2026年7月预算.xlsx`，保留正确命名的 8 月文件。

## 设计

预算服务新增一个纯校验边界：在 `listBudgetTargets()` 汇集已解析摘要后，按规范化店铺名和预算月份分组。若任一组超过一项，则抛出专用的预算完整性错误。错误文本包含店铺、月份与冲突的原始文件名，供 API、日志和 UI 直接显示。

`getBudgetTargetContext()` 继续以 `listBudgetTargets()` 为唯一入口，因此销售复盘、店铺月报和所有预算消费者均会收到同样的失败语义。不会在 MSKU 映射器、负责人筛选或前端表格中加入去重逻辑。

既有上传覆盖逻辑保持不变：正常上传新的同店同月预算时仍会删除旧上传。新增校验覆盖历史文件、手工迁移或旧版本重新解析遗留的冲突。

## 可观测性与错误处理

冲突错误会保留所有冲突键和文件名。调用方不允许将其转换为空预算、零预算或旧缓存；服务器的既有错误响应将使页面明确显示加载失败。

## 验证

1. 先新增服务测试，证明两个同店同月的历史摘要会被拒绝，且错误包含两个文件名。
2. 验证不同店铺或不同月份仍可共同存在。
3. 运行聚焦测试、完整 `npm test` 与 `npm run check`。
4. 在生产服务器删除已确认的误标 7 月文件及其摘要，并清理销售周会源缓存和 MSKU 明细缓存，使下一次请求基于唯一的 8 月预算重建。
5. 通过生产健康接口和销售复盘请求验证无重复键；不泄露领星凭据或响应中的敏感字段。

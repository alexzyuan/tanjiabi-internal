# 库存分类账原始报表自动拉取与全量重建设计

## 目标

从领星可导出的库存分类账完整原始报告文件重建库存计提历史缓存。服务器在每月 10 日为上个月创建 `GET_LEDGER_DETAIL_VIEW_DATA` 导出任务，只有成功下载、留档、校验并解析全部报告后，才从固定起始月 `2025-10` 开始全量重建到上个月；不增加前端下载按钮。

当前立即运行一次 `2025-10` 至上个月的全量重建；以后每月 10 日自动处理上个月。例如当前运行时间为 2026 年 8 月时，范围为 `2025-10-01` 至 `2026-07-31`。

本文描述正式启用后的目标行为；生产环境只有在包含该实现的版本完成部署后才切换到该来源。

## 已确认口径

- 原始数据源为领星 `GET_LEDGER_DETAIL_VIEW_DATA` 的可导出完整报告文件，不是已废弃的 Daily Inventory 接口。一个月、一个卖家范围对应一个导出任务；任务必须完成并提供可下载文件，才能作为重建输入。
- 从 `2024-10` 起的导出分类账报告是唯一 FIFO 输入。报告序列必须包含能建立开账数量的分类账事件；如果开账缺失、未知事件或之后任一出库无法闭合，重建必须失败。不得调用 FBA 月末库存 JSON API、旧缓存或猜测的较新批次补齐。
- 报告按月份导出并保存；本次重建范围固定为 `2025-10` 至上个月，包含跨年月份。
- 原始报告文件是可审计输入。服务器保存未改写的下载二进制和带 SHA-256 的 manifest；重建只解析已验证的报告文件，不在页面查询时重新历遍 Listing 或重复请求库存流水。
- `/cost/center/ods/detail/query` 可以用于排障或与报告核对，但不是正式重建输入，导出任务失败时不得回退到该接口。
- 使用库存分类账事件计算 FIFO 批次和库龄；采购成本、头程成本继续由现有成本刷新流程读取产品管理当前值，属于独立步骤，不在本任务中自动调用成本刷新接口。
- 当前月不参与历史全量重建；若上个月报表尚未成功下载，任务失败且不覆盖任何历史缓存。

## 方案选择

### 方案 A（采用）：官方导出报告留档并离线重建

每个卖家范围按月份创建报告导出任务，轮询至完成，按需续期下载链接，下载完整原始报告二进制并保存其 manifest。只有 SHA-256 与 manifest 一致的文件才会被解析；解析完所有已保存月份并通过覆盖范围校验后，才构建新的月份缓存并原子替换。优点是数据可追溯、可重复重建、页面查询无外部延迟；代价是需要管理任务生命周期、下载、文件完整性、历史种子区间和磁盘清单。

### 方案 B：仅调用 API 而不留档

定时查询 `/cost/center/ods/detail/query` 或 summary 接口并直接写缓存。实现较少，但并非正式原始报告文件，无法满足以可导出报告作为唯一重建输入的要求。

### 方案 C：原始报表仅作备份，重建仍调用明细 API

同时保存原始文件和调用 `/cost/center/ods/detail/query`。这会产生两套输入，原始文件不能真正驱动重建，长期排查成本高。

采用方案 A。

## 架构与模块边界

### `src/adapters/lingxingAdapter.js`

提供报告导出协议：创建 `GET_LEDGER_DETAIL_VIEW_DATA` 任务、查询任务状态、按需续期下载链接和下载二进制文件。适配器只负责领星协议，不负责文件命名、解析或缓存写入。`/cost/center/ods/detail/query` 保留为诊断/核对调用，不参与正式重建。

### `src/services/inventoryLedgerRawReportService.js`（新增）

拥有一次报表同步和重建的业务编排：

1. 计算 `2025-10` 至上个月的月份清单和卖家/区域范围。
2. 对每个源月、每个范围创建报告导出任务，轮询完成、按需续期 URL，并下载 `GET_LEDGER_DETAIL_VIEW_DATA` 原始报告；不读取 FBA 月末库存 JSON 快照。
3. 将下载的原始报告二进制和 manifest 原子写入 `data-cache/inventory-ledger-raw/<YYYY-MM>/`。manifest 记录 seller/region、日期范围、报告类型、任务/文档标识、压缩方式、字节数、SHA-256、获取时间和解析行数；不得记录 access token 或报告内容。
4. 解析所有目标月份已保存的原始文件，规范化事件日期、卖家、MSKU、仓库、数量、事件类型和 disposition，拒绝无法识别的必需列或日期越界数据。
5. 以规范化事件集合调用库存计提的批次重建逻辑，生成各目标月份的完整缓存数据；保留现有店铺、负责人、成本字段及既有计提口径，数量和库龄以分类账重建结果为准。
6. 所有月份都通过校验后，写入临时批次目录并执行原子替换；任一下载、解析、覆盖范围、重建或写入失败均保留旧的 `inventory-provision-history`，不得部分成功。

服务暴露：

- `runInventoryLedgerRawRebuild({ force, dryRun, now })`：调度器和受控手工运维入口共用；`force` 仅重新拉取/重建指定目标周期，`dryRun` 执行同样的读取、解析与 FIFO 校验但不留档、不提交，不提供前端下载操作。
- `getInventoryLedgerRawRebuildStatus()`：返回最近成功/失败、目标范围、报表清单状态、文件数量、解析行数和失败阶段，供健康检查或后台状态使用。

### `src/jobs/inventoryLedgerRawRebuildJob.js`（新增）

使用 `Asia/Shanghai` 日历和现有 `withJobLock`：每 5 分钟检查一次，10 日 `02:00` 以后若上个月尚未成功则执行；同一上海自然日只自动尝试一次，失败留待次日重试，避免持续重复提交同一批任务。成功和失败状态均持久化到 `data-cache/inventory-ledger-raw/job-state.json`；失败记录阶段、月份、卖家、任务号、上游状态和可重试信息。应用启动时只做一次“是否到时间”的检查，不在非计划日期拉取。

### `src/services/inventoryLedgerRawReportStore.js`

拥有原始报告二进制目录、manifest、作业状态和 staging/commit 所需的受控读写接口；保存后和解析前均以 SHA-256 校验完整性。现有 `src/utils/cacheStore.js` 历史缓存读取接口保持兼容。原始报告不参与普通缓存 TTL 清理，且文件 I/O 不进入通用 JSON 缓存层。

### `src/services/inventoryProvisionService.js`

提取或扩展纯批次重建入口，使其可以接收规范化分类账事件和目标月份；保持现有页面加载、当前月实时库存、计提比例和成本刷新行为不变。不得把报表下载、轮询或文件系统逻辑放入该服务。

### `server.js`

启动新的日历 job。若增加状态接口，只提供只读的受保护运维状态；不增加下载按钮、不让浏览器直接访问原始报表文件。

## 数据流

```mermaid
flowchart LR
  A[每月10日调度器] --> B[创建并轮询领星导出任务]
  B --> C[下载GET_LEDGER_DETAIL_VIEW_DATA原始报告]
  C --> D[报告二进制与SHA-256 manifest原子留档]
  D --> E[解析并校验2024-10种子至上月]
  E --> F[按FIFO重建月度批次]
  F --> G[staging生成全部历史缓存]
  G --> H[全量校验通过后原子替换]
  H --> I[页面读取库存计提缓存]
```

同一月份若已有成功 manifest，普通定时运行只复用通过 SHA-256 校验的报告并重建；`force` 才重新创建导出任务。任务创建、轮询、下载或 URL 续期失败，文件哈希/格式错误、必需字段缺失、事件日期越界、FIFO 无法闭合或缓存写入失败，均产生明确错误并保持旧缓存；不得静默调用明细 API 替代。

## 一致性与可观测性

- 原始文件、manifest、job state 和历史缓存均使用临时文件 + rename；不能留下“成功”状态但文件不完整的记录。
- 每次运行生成 `runId`，日志包含阶段、目标月份、seller/region 数、任务数、下载字节数、解析行数、重建行数、耗时和 commit 结果；认证信息和完整原始响应禁止写入日志。
- 成功状态必须包含实际原始报表获取时间与重建时间，页面已有的“成本缓存刷新时间”不冒充库存源更新时间。
- 失败重试不删除旧成功 manifest；失败尝试只写入 job state，不伪造失败 manifest，下一次调度可继续。

## 测试与验收

自动化测试覆盖：

1. 月份计算：每月 10 日拉上个月，跨年从 `2025-10` 到上个月；9 日不执行，10 日后同一周期成功后不重复执行。
2. 导出任务的请求参数、完成状态、失败状态、超时和下载 URL 续期。
3. 导出任务创建、轮询、URL 续期、下载、报告解析、必需字段校验、事件日期范围校验、SHA-256 不匹配拒绝、重复留档幂等与 dry-run 无写入。
4. 从固定 fixture 全量重建多个月份，数量/批次/库龄与预期一致；任一月份失败时旧缓存完全不变。
5. job lock 防止多实例并发，失败状态可观测且下一次可重试。
6. 现有库存计提、成本刷新、全量 Node 测试和静态检查不回归。

验收时先在本地 fixture 执行一次全量重建；生产部署后只运行“拉取原始报表并重建”的受控任务，不自动调用成本刷新接口。生产包仍必须通过现有部署 manifest 和分支校验。

## 不在范围内

- 不增加前端下载按钮或让前端直接调用报表导出接口。
- 不修改 Listing 匹配规则、产品管理成本取值规则或成本刷新接口。
- 不自动修改领星报表设置，不调用库存成本写回接口。
- 不删除既有历史缓存或原始报表；旧缓存只在新批次全量校验通过后替换。

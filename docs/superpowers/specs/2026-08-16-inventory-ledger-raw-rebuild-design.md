# 库存分类账原始报表自动拉取与全量重建设计

## 目标

从领星导出的亚马逊库存分类账原始报表重建库存计提历史缓存。服务器在每月 10 日自动拉取上个月的报表，原始文件留存在服务器；每次成功取得报表后，从固定起始月 `2025-10` 开始全量重建到上个月，不增加前端下载按钮。

当前立即运行一次 `2025-10` 至上个月的全量重建；以后每月 10 日自动处理上个月。例如当前运行时间为 2026 年 8 月时，范围为 `2025-10-01` 至 `2026-07-31`。

## 已确认口径

- 原始数据源为领星报表导出接口对应的亚马逊 `GET_LEDGER_DETAIL_VIEW_DATA`（库存分类账明细），不是已废弃的 Daily Inventory 接口。
- 报表按月份请求并保存；本次重建范围固定为 `2025-10` 至上个月，包含跨年月份。
- 原始报表是可审计输入。重建读取已保存的原始文件，不在页面查询时重新历遍 Listing 或重复请求库存流水。
- 使用库存分类账事件计算 FIFO 批次和库龄；采购成本、头程成本继续由现有成本刷新流程读取产品管理当前值，属于独立步骤，不在本任务中自动调用成本刷新接口。
- 当前月不参与历史全量重建；若上个月报表尚未成功下载，任务失败且不覆盖任何历史缓存。

## 方案选择

### 方案 A（采用）：原始明细报表留档并离线重建

每个卖家/区域按月份创建报表导出任务，轮询到完成后下载压缩文件，保存文件和清单，再解析所有已保存月份的事件，校验覆盖范围后构建新的月份缓存，最后原子替换。优点是数据可追溯、可重复重建、页面查询无外部延迟；代价是需要下载轮询、压缩/TSV 解析和磁盘清单管理。

### 方案 B：直接调用标准化库存流水 API

定时查询 `/cost/center/ods/detail/query` 或 summary 接口并直接写缓存。实现较少，但无法留存领星原始报表，且源数据变化后不能复现当时口径。

### 方案 C：原始报表仅作备份，重建仍调用标准化 API

同时保存原始文件和调用标准化 API。审计性较好但存在两套口径，原始文件不能真正驱动重建，长期排查成本高。

采用方案 A。

## 架构与模块边界

### `src/adapters/lingxingAdapter.js`

扩展报表导出适配器：创建导出任务、查询任务状态、续期下载 URL，并提供经过超时与 HTTP 错误检查的二进制下载入口。适配器只负责领星协议，不负责文件命名、解析或缓存写入。

### `src/services/inventoryLedgerRawReportService.js`（新增）

拥有一次报表同步和重建的业务编排：

1. 计算 `2025-10` 至上个月的月份清单和卖家/区域范围。
2. 对缺少成功清单的月份创建 `GET_LEDGER_DETAIL_VIEW_DATA` 导出任务，轮询完成状态，下载并校验非空文件，计算 SHA-256。
3. 将原始压缩文件和 JSON manifest 原子写入 `data-cache/inventory-ledger-raw/<YYYY-MM>/`。manifest 记录 seller/region、日期范围、report type、task id、document id、压缩方式、字节数、哈希、获取时间和解析行数；不得记录 access token 或完整外部响应。
4. 解析所有目标月份已保存的原始文件，规范化事件日期、卖家、MSKU、仓库、数量、事件类型和 disposition，拒绝无法识别的必需列或日期越界数据。
5. 以规范化事件集合调用库存计提的批次重建逻辑，生成各目标月份的完整缓存数据；保留现有店铺、负责人、成本字段及既有计提口径，数量和库龄以分类账重建结果为准。
6. 所有月份都通过校验后，写入临时批次目录并执行原子替换；任一下载、解析、覆盖范围、重建或写入失败均保留旧的 `inventory-provision-history`，不得部分成功。

服务暴露：

- `runInventoryLedgerRawRebuild({ force, now })`：调度器和受控手工运维入口共用；`force` 仅重新拉取/重建指定目标周期，不提供前端下载操作。
- `getInventoryLedgerRawRebuildStatus()`：返回最近成功/失败、目标范围、报表清单状态、文件数量、解析行数和失败阶段，供健康检查或后台状态使用。

### `src/jobs/inventoryLedgerRawRebuildJob.js`（新增）

使用 `Asia/Shanghai` 日历和现有 `withJobLock`：每 5 分钟检查一次，10 日 `02:00` 以后若上个月尚未成功则执行；成功状态持久化到 `data-cache/inventory-ledger-raw/job-state.json`，失败记录阶段和可重试信息。应用启动时只做一次“是否到时间”的检查，不在非计划日期拉取。

### `src/services/inventoryLedgerRawReportStore.js`

拥有原始报表目录、manifest、作业状态和 staging/commit 所需的受控读写接口；现有 `src/utils/cacheStore.js` 历史缓存读取接口保持兼容。原始文件不参与普通缓存 TTL 清理，且二进制 I/O 不进入通用 JSON 缓存层。

### `src/services/inventoryProvisionService.js`

提取或扩展纯批次重建入口，使其可以接收规范化分类账事件和目标月份；保持现有页面加载、当前月实时库存、计提比例和成本刷新行为不变。不得把报表下载、轮询或文件系统逻辑放入该服务。

### `server.js`

启动新的日历 job。若增加状态接口，只提供只读的受保护运维状态；不增加下载按钮、不让浏览器直接访问原始报表文件。

## 数据流

```mermaid
flowchart LR
  A[每月10日调度器] --> B[创建/轮询领星导出任务]
  B --> C[服务器下载原始分类账]
  C --> D[文件与manifest原子留档]
  D --> E[解析并校验2025-10至上月]
  E --> F[按FIFO重建月度批次]
  F --> G[staging生成全部历史缓存]
  G --> H[全量校验通过后原子替换]
  H --> I[页面读取库存计提缓存]
```

同一月份若已有成功 manifest，普通定时运行只复用文件并重建；`force` 才重新申请报表。导出任务等待超时、下载 URL 过期、文件哈希/格式错误、必需列缺失、事件日期越界、目标月份无数据或缓存写入失败，均产生明确错误并保持旧缓存。

## 一致性与可观测性

- 原始文件、manifest、job state 和历史缓存均使用临时文件 + rename；不能留下“成功”状态但文件不完整的记录。
- 每次运行生成 `runId`，日志包含阶段、目标月份、seller/region 数、任务数、下载字节数、解析行数、重建行数、耗时和 commit 结果；认证信息和完整原始响应禁止写入日志。
- 成功状态必须包含实际原始报表获取时间与重建时间，页面已有的“成本缓存刷新时间”不冒充库存源更新时间。
- 失败重试不删除旧成功 manifest；新失败 manifest 作为最近尝试记录，下一次调度可继续。

## 测试与验收

自动化测试覆盖：

1. 月份计算：每月 10 日拉上个月，跨年从 `2025-10` 到上个月；9 日不执行，10 日后同一周期成功后不重复执行。
2. 导出任务创建、状态轮询、下载 URL 续期、超时和非 2xx/坏文件失败。
3. gzip/TSV 原始报表解析、必需列校验、事件日期范围校验和重复文件幂等。
4. 从固定 fixture 全量重建多个月份，数量/批次/库龄与预期一致；任一月份失败时旧缓存完全不变。
5. job lock 防止多实例并发，失败状态可观测且下一次可重试。
6. 现有库存计提、成本刷新、全量 Node 测试和静态检查不回归。

验收时先在本地 fixture 执行一次全量重建；生产部署后只运行“拉取原始报表并重建”的受控任务，不自动调用成本刷新接口。生产包仍必须通过现有部署 manifest 和分支校验。

## 不在范围内

- 不增加前端下载按钮或让前端直接调用报表导出接口。
- 不修改 Listing 匹配规则、产品管理成本取值规则或成本刷新接口。
- 不自动修改领星报表设置，不调用库存成本写回接口。
- 不删除既有历史缓存或原始报表；旧缓存只在新批次全量校验通过后替换。
